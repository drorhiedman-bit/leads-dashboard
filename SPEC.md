# SPEC: Smart Lead Dashboard for a Solo Plumber

## 1. Who

Primary user: a solo plumber, about 40 years old, in the Jezreel Valley.
He works alone, mostly outdoors and on job sites, and uses the dashboard
almost only on his phone, often with one free hand, dirty hands or gloves,
and in bright sunlight. He loses jobs by calling back too late or by
chasing the wrong leads, and many competitors operate in the same area.
He does not want to learn an app. He needs one screen that answers:
"Who do I call first?"
Design rules that follow from this user:

- Mobile first. Design for a 360 px wide phone screen, then scale up.
- One scrolling page. No popups, no tabs, no multi-step windows.
- Few numbers on screen, with the most important thing first.
- Large buttons: at least 48 x 48 px, with space between them.
- Body text at least 16 px. Urgent items in bold.

## 2. What / What not

WHAT: A dashboard that scores every incoming lead from 0 to 100, shows a
"Call now" list of the top 5 leads, the sales funnel, which lead source
pays off, and how much money is in the pipeline. A small weather strip shows the next 3 days in the service area,
with a work hint for the plumber (frost or heavy rain).
WHAT NOT: no user login, no sending of messages or emails, no writing to
the database. The dashboard only reads. The leads are made-up sample
leads, not real customers.

## 3. Where

A static web page that opens in any browser, with no server.
Files: index.html, style.css, app.js, data.js and weather.js. data.js
and weather.js are not kept in the repository: they are generated by
scripts (see sections 4 and 4a).
Plain HTML, CSS and JavaScript. No external libraries. Charts are built
with CSS only. Published on GitHub Pages by a GitHub Actions workflow.
UI language: Hebrew, right to left (lang="he", dir="rtl").
On a phone each lead is a card. On a wide screen the cards may be shown
as a table.

## 4. Data

The leads live in an Airtable base, in one table named Leads. Airtable
is the single source of truth: leads are added and changed only there.
30 sample leads. Each lead has: id, name, phone, town, job type,
urgency (1-5), estimated value in ILS, source, distance in km,
received time (minutes ago), stage.
Stages: New, Contacted, Quote sent, Won, Lost.
Sources: Referral, Repeat customer, Google, Facebook, Facebook group.
Job types with typical value: blocked drain 250-500, faucet 200-400,
leak repair 300-800, burst pipe 600-1500, water heater 1500-3500,
bathroom renovation 12000-30000.
The 30 leads are spread across all stages and all sources, and include
at least 3 emergencies and 3 New leads that waited over 3 hours.
Towns are in the Jezreel Valley area. Service area: up to 40 km from
Moshav HaYogev.

How the data reaches the page:

1. A script (scripts/fetch-leads.mjs) reads the Leads table through the
   Airtable API and writes data.js. It runs in a GitHub Actions workflow
   once an hour, on every push to main, and on demand, and then the
   workflow publishes the site.
2. The page loads data.js. The page itself never talks to Airtable and
   never holds a token.

Data rules, checked by the script before it writes anything:

- Every lead has all the fields above. Urgency is a whole number 1-5.
  Value and distance are numbers, zero or more.
- Stage, source and job type are one of the values listed above.
- A lead that breaks a rule is not written. The script lists it with
  the reason and fails, so a bad lead never reaches the page silently.
- The script prints how many leads it read and how many it wrote.

Who may do what:

- Dror: adds and edits leads in Airtable.
- The script: read only. Its token has the scope data.records:read on
  this one base and nothing else.
- Visitors of the page: see the dashboard, with no access to Airtable.

The token is a secret. On a computer it lives in a .env file that is
never committed (.gitignore). On GitHub it lives in repository Secrets
as AIRTABLE_TOKEN. A committed .env.example shows the names without the
values.

## 4a. Weather forecast (public API, bonus)

Source: Open-Meteo (open-meteo.com), a free public weather API with no
key and no account. Free for non-commercial use, so it fits this
sample project. A real paying customer would need its commercial plan.
Place: Moshav HaYogev (latitude 32.61, longitude 35.20), time zone
Asia/Jerusalem. Three days: today, tomorrow and the day after.
For each day: date, lowest and highest temperature (C), total rain
(mm), and the weather code.

How the data reaches the page:

1. A second script (scripts/fetch-weather.mjs) asks Open-Meteo for the
   forecast and writes weather.js. It runs in the same workflow as the
   leads script, before the site is published.
2. The page loads weather.js. The page itself never talks to
   Open-Meteo. There is no token and no secret.

Data rules, checked by the script:

- Exactly 3 days. Every value is present and is a number.
  Lowest temperature is not above highest. Rain is zero or more.
- If Open-Meteo does not answer within 10 seconds, or the answer breaks
  a rule, the script writes an empty forecast and prints why, but it
  does NOT fail the workflow. The leads are more important than the
  weather, so the dashboard is still published, and the strip says
  "Forecast not available right now".
- The script prints the 3 days it wrote.

Work hint for each day (first rule that matches):

1. Lowest temperature 2 C or less: "Frost: expect burst pipe calls".
2. Rain 15 mm or more: "Heavy rain: expect blocked drains and leaks".
3. Otherwise: "Regular day".
A hint is always shown with a word and an icon, never color alone.

Credit: the footer says "Weather data: Open-Meteo.com" with a link, as
Open-Meteo asks (license CC BY 4.0).

## 5. Lead score (0-100)

- Job value, up to 30: over 5000 = 30, 1500-5000 = 24, 600-1500 = 17,
  300-600 = 10, under 300 = 5.
- Urgency, up to 25: level 5 = 25, 4 = 20, 3 = 15, 2 = 10, 1 = 5.
  Urgency is the customer's problem and does not change over time.
- Waiting time, up to 20 (only for leads in stage New): up to 15 minutes
  = 20, 15-60 minutes = 15, 1-3 hours = 8, over 3 hours = 3.
  Waiting time is how long the lead has waited for a reply.
  The shorter the wait, the more points.
  Leads in other stages get 0 for this factor.
- Source, up to 15: repeat customer 15, referral 13, Google 9,
  Facebook group 7, Facebook 5.
- Distance, up to 10: up to 10 km = 10, 10-25 km = 7, 25-40 km = 3,
  over 40 km = 0.

Score levels, always shown with a word and not only a color:
70 and up = High, 40-69 = Medium, under 40 = Low.

## 6. Screen order (top to bottom, one page)

1. Call now: 5 cards, highest score first, only stages New or Contacted.
   Each card shows name, job, town, score with level word, and a large
   "Call" button that dials the phone (tel: link).
2. Weather strip: 3 small day cards in one row (date, weather word,
   low and high temperature, rain, work hint). On a 360 px screen it
   fits without horizontal scrolling.
3. Three big numbers: money in pipeline, new leads today, closing rate.
4. Funnel chart: horizontal bars, one per stage, with the count on each.
5. Best source chart: one horizontal bar per source, length by closing
   percentage, with the number shown.
6. All leads: closed by default, opens with a "Show all" button.
   Each lead card shows name, job, town, source, stage and score.
   Sorted by score.

## 7. Features

MUST (version 1):

1. Lead score as defined in section 5, with the factor breakdown
   visible when a card is tapped.
2. Call now list (section 6, item 1).
3. Sales funnel with counts and conversion percentage from New to Won.
4. Best source: for each source, number of leads, number Won, closing %.
5. Money in pipeline: total estimated value of leads in Contacted and
   Quote sent, and the total value of Won leads.
6. All leads list as cards (section 6, item 6).

SHOULD:

8. Filter the all-leads list by stage and by source.

BONUS (lesson 4):

## 8. Design and accessibility

Theme: sea and sand, a calm vacation feel.
Colors: page background sand #F6EBD3, cards #FFFDF8, text deep sea
#0B2A4A, buttons and headings sea blue #0A5C8F, highlight turquoise
#8FD3DC, borders sand #E9CF9A, urgent alert coral #B53A22 (alerts only).
Score levels: High = deep blue, Medium = sand, Low = blue-gray.
Accessibility, aiming for WCAG AA and the Israeli standard SI 5568:

- Contrast at least 4.5:1 for text, 3:1 for large text and controls.
- Never use color alone. Always add a word or an icon.
- Correct heading order, labels for buttons, keyboard navigation with a
  clearly visible focus outline.
- Respect the user's text-size settings. No fixed tiny text.
- Reduce animation for users who ask for it (prefers-reduced-motion).

## 9. Done means

1. Opening index.html shows 30 leads and no console errors.
2. The Call now list shows exactly 5 leads, all in stage New or
   Contacted, sorted by score, and each has a working Call button.
3. Funnel counts add up to 30.
4. Pipeline total equals the sum of values of Contacted and Quote sent
   leads, checked by hand against the Leads table in Airtable.
5. On a 360 px wide screen there is no horizontal scrolling and all
   buttons are at least 48 px.
6. Text contrast passes a WCAG AA check, and each score has a word.
7. The page is live on GitHub Pages (bonus).
8. The weather strip shows 3 days with a work hint each, and the
   numbers match the Open-Meteo forecast printed in the workflow log.
9. When Open-Meteo is unreachable, the workflow still succeeds, the
   leads still show, and the strip says the forecast is not available.
